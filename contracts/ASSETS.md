# Asset Contract

The optional `asset` starter owns the private lifecycle of user-uploaded objects. It depends on the
default `user` and `audit` starters and uses the object-storage capability without exposing provider
SDKs, bucket names, object keys, or local paths to feature code.

An **asset** is the user-owned metadata and lifecycle record. A **stored object** is the opaque byte
payload behind the capability seam. These terms are deliberately separate: a browser `File`, a local
filesystem path, and an R2/S3 object are transport or provider details, not asset identity.

## Activation

Enable the API starter for every API process, migration job, and cleanup job:

```dotenv
OPTIONAL_STARTERS=asset
```

Enable the matching browser feature in the same Web build:

```dotenv
NEXT_PUBLIC_OPTIONAL_FEATURES=asset
```

Selection is additive and restart-scoped. The API defaults to local object storage outside
production and requires an explicitly configured supported remote driver in production. The Web
feature never fabricates production assets when neither the fixed production adapter nor the
development mock BFF is available.

## Ownership And Identity

- Every asset belongs to exactly one authenticated Luas user.
- Asset IDs are application-generated UUIDs and are the only object identifiers exposed over HTTP.
- Owner user IDs, bucket names, object keys, local paths, checksums, and signed-token claims are not
  returned to the browser.
- A lookup for a missing asset and a lookup for another user's asset both return
  `404 ASSET.NOT_FOUND`.
- Organization, public, shared, and polymorphic ownership are deliberately outside this starter.

## Lifecycle

Asset states are:

| State | Meaning |
|---|---|
| `pending` | Metadata and an expiring upload intent exist; the object is not downloadable |
| `ready` | Stored bytes passed metadata and content inspection and were promoted to an immutable final key |
| `rejected` | Completion found missing, oversized, mismatched, or unsupported content |
| `deleted` | The owner deleted the asset; the object is unavailable and the tombstone is retained |

The only forward transitions are `pending -> ready`, `pending -> rejected`, and
`pending|ready|rejected -> deleted`. Repeating completion for a ready asset returns the same asset.
Repeating deletion by the same owner succeeds without restoring metadata or bytes.

An upload URL writes only to a random staging key. Completion first copies the staged object to a
distinct immutable final key, then validates that frozen final snapshot before marking the asset
ready. This order closes the staging inspect/copy race: a still-valid upload URL can overwrite only
staging bytes; it cannot replace the inspected final object or mutate a ready asset.

## Upload Policy

Create an upload intent with:

```json
{
  "idempotency_key": "019bf6d8-17c5-7a98-a084-6d45793f5f0c",
  "original_name": "quarterly-report.pdf",
  "media_type": "application/pdf",
  "size_bytes": 248103
}
```

Rules:

- `idempotency_key` is 1-128 ASCII letters, digits, `.`, `_`, `:`, or `-`.
- `(owner_user_id, idempotency_key)` is unique. An identical replay returns the existing asset and a
  fresh upload grant while it remains pending. A replay with different immutable metadata fails.
- `original_name` is trimmed UTF-8, 1-255 bytes, contains no path separator or control character,
  and uses an extension allowed for the declared media type.
- `media_type` must be an exact code-owned allowlist value. Parameters such as `charset` are not
  accepted in the intent.
- `size_bytes` must be positive and no larger than the configured maximum, which defaults to
  10 MiB.
- Object keys are generated by the application and never derived from `original_name`.

The first shipped allowlist covers JPEG, PNG, WebP, PDF, UTF-8 plain text, and UTF-8 CSV. SVG, HTML,
archives, executable formats, and ambiguous binary content are denied by default. Downstream apps
may replace the policy deliberately; they must not trust the request `Content-Type` alone.

Successful creation returns HTTP 201 with a private, non-cacheable grant:

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "asset": {
      "id": "019bf6d8-17c5-7a98-a084-6d45793f5f0c",
      "original_name": "quarterly-report.pdf",
      "media_type": "application/pdf",
      "size_bytes": 248103,
      "status": "pending",
      "created_at": "2026-07-15T20:00:00Z",
      "ready_at": null
    },
    "upload": {
      "method": "PUT",
      "url": "https://storage.example/signed-request",
      "headers": {
        "content-type": "application/pdf"
      },
      "expires_at": "2026-07-15T20:10:00Z"
    }
  }
}
```

The signed URL and its query are bearer credentials. They are never logged, audited, persisted in
the asset table, placed in analytics, or returned by list/detail endpoints. Browser callers must send
exactly the returned method and required headers. Provider CORS must allow the application origin,
`PUT`, and the required headers.

Remote PUT presigning cannot reliably enforce body length across every S3-compatible provider.
Completion therefore checks authoritative object metadata and streams at most the configured limit
plus one byte. Operators must also apply a short lifecycle rule to the staging prefix; `asset:prune`
is the application-side cleanup backstop.

## Completion And Inspection

`POST /v1/assets/:id/complete` performs all of the following before readiness:

1. revalidates owner and `pending` state;
2. confirms the pending lifetime has not expired;
3. reads authoritative staging size and media type;
4. freezes staging bytes under a separate immutable final key;
5. rechecks final size/media metadata and streams the bounded final object through the inspector;
6. verifies detected content against the code-owned media policy and computes SHA-256 internally;
7. removes the current staging bytes while retaining its private cleanup key until grant expiry;
8. marks the row `ready` and emits privacy-minimized audit metadata.

The default inspector validates signatures for JPEG, PNG, WebP, and PDF, and rejects NUL-containing
or invalid UTF-8 text/CSV. It is a content-integrity baseline, not an antivirus claim. Downstream apps
that accept untrusted documents should compose a malware scanner or sandbox at the inspector seam
before making content available.

Failed inspection deletes staging bytes best-effort, marks the asset `rejected`, and never creates a
download grant. A storage or database availability failure does not silently convert the row to
ready.

## HTTP API

All management endpoints require the standard bearer token and operate only on the authenticated
user's data. List results are paginated, exclude deleted rows, and are ordered newest first.

| Operation | Endpoint | Success |
|---|---|---|
| List assets | `GET /v1/assets?status=all\|pending\|ready\|rejected` | Paginated assets |
| Create upload intent | `POST /v1/assets/upload-intents` | HTTP 201 `{ asset, upload }` |
| Complete upload | `POST /v1/assets/:id/complete` | Asset |
| Create download grant | `POST /v1/assets/:id/download-grant` | `{ method, url, headers, expires_at }` |
| Delete asset | `DELETE /v1/assets/:id` | `{ deleted: true }` |

A ready asset response is:

```json
{
  "id": "019bf6d8-17c5-7a98-a084-6d45793f5f0c",
  "original_name": "quarterly-report.pdf",
  "media_type": "application/pdf",
  "size_bytes": 248103,
  "status": "ready",
  "created_at": "2026-07-15T20:00:00Z",
  "ready_at": "2026-07-15T20:00:04Z"
}
```

Download grants are short-lived bearer credentials and force attachment disposition. The response
does not contain a durable or public URL. A not-ready asset returns `409 ASSET.NOT_READY`.

## Browser Adapter

The fixed same-origin adapter mirrors management operations under `/api/assets`. Successful upstream
and mock JSON is strictly validated before entering React Query state. Unsafe management operations
enforce same-origin checks before authentication or body parsing. Management and grant responses use
`Cache-Control: private, no-store` and `Vary: Cookie`.

The browser uploads bytes directly to the returned grant URL and then calls completion. It accepts
only an `https:` URL or the exact same-origin mock/local transfer path; redirects, credentials in
URLs, protocol-relative values, and unsupported methods are rejected before transfer. Signed URL
query values are never copied into toast text, error detail, logs, or persistent client state.

The development mock BFF preserves user isolation, idempotency, state transitions, size/media rules,
download attachment behavior, and stable errors. It is a local substitute, not a production object
store.

## Deletion And Account Integrity

Delete removes staging and final objects best-effort before recording the tombstone. A missing object
is treated as already removed. Database failures remain retryable; a deleted object is never made
downloadable merely because the tombstone write must be retried. Because a provider-native PUT grant
cannot be revoked, the tombstone retains its private cleanup keys until the pending lifetime has
ended. The cleanup job then repeats deletion and clears those keys, so an upload arriving after the
user-visible delete cannot become an orphaned stored object.

The starter registers an account-deletion guard. A user must delete active asset rows before account
deletion so provider objects cannot be orphaned by a database cascade. Asset creation locks the same
user row before inserting metadata, and the guard reads through the account-deletion transaction, so
create/delete races cannot attach active assets to a soft-deleted user. Cleanup jobs remove expired
pending/rejected/deleted objects and any late ready-state staging write after all upload grants have
expired; ready final objects are preserved. Jobs report counts without logging names, keys, signed
URLs, or checksums.

## Audit And Privacy

Create, ready, rejected, and delete operations emit asset ID, status, media type, size, and stable
reason codes where relevant. Original names, object keys, local paths, checksums, signed URLs,
provider responses, and byte content are excluded from audit metadata and logs.

Asset metadata and stored bytes require a downstream retention and backup policy. Signed URLs must be
treated like credentials, and object-storage access logs must use provider-side redaction and access
controls appropriate to the deployment.

## Stable Errors

| HTTP status | `error_code` | Meaning |
|---|---|---|
| 404 | `ASSET.NOT_FOUND` | Asset is absent, deleted, or owned by another user |
| 409 | `ASSET.NOT_READY` | Download or completion conflicts with the current lifecycle state |
| 409 | `ASSET.IDEMPOTENCY_CONFLICT` | An idempotency key was reused with different immutable metadata |
| 409 | `ASSET.CLEANUP_REQUIRED` | Active assets must be deleted before account deletion |
| 410 | `ASSET.UPLOAD_EXPIRED` | Pending upload lifetime elapsed before completion |
| 413 | `ASSET.SIZE_EXCEEDED` | Declared or authoritative object size exceeds the asset policy |
| 422 | `ASSET.INVALID_MEDIA_TYPE` | Media type, extension, or detected content is unsupported or inconsistent |
| 503 | `COMMON.SERVICE_UNAVAILABLE` | Persistence, inspection, or object storage is unavailable |

Malformed JSON, field validation, global envelopes, and `request_id` behavior follow
[`README.md`](README.md).

## Deliberate Deferrals

The starter does not ship public assets, organization ownership, sharing, folders, tags, image
variants, previews, content delivery networks, multipart or resumable upload, quota/usage accounting,
versioning, legal hold, a fixed antivirus provider, or a generalized media library. Those concerns
can extend the ownership, inspection, transformation, and usage seams without changing asset identity
or exposing provider keys.
